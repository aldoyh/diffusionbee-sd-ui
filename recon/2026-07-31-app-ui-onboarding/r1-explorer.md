# R1 Explorer — The Territory: DiffusionBee's Entire UI & Onboarding

**Round 1 (Explore, divergent).** Method: targeted reads of every page in `electron_app/src/pages/`, the shell (`App.vue`, `PagesRouter.vue`, `pageMeta.js`), the demo surfaces, and a firsthand PYZ/table-of-contents dump of the packaged backend binary at `electron_app/.packaged-backend/diffusionbee_backend` (the same bytes the installed `/Applications/diffusion-sd-ui.app` ships). Web primary sources fetched directly: diffusionbee.com, the upstream GitHub repo (README, releases, issues, API), the live model catalog, and the upstream update server. Settled claims from the brief are treated as given and only extended where the code has moved past them.

---

## (a) Page inventory — thirteen pages, three generations of craft

`electron_app/src/pages/pageMeta.js` is the navigation source of truth, and its first surprise is structural: `PagesRouter.vue:75` loads **all** of `pageMeta` into `always_on_pages` and the template (`PagesRouter.vue:6-8`) renders **every page at once**, hidden with `display:none` and revealed by the `bl_display` class. The `() => import(...)` "lazy" wrappers (`PagesRouter.vue:40-49`) only code-split the webpack chunks — every page component still instantiates on first paint, because the `v-for` renders them all immediately. Only `Homepage` and `History` are eager *imports* (`PagesRouter.vue:36-37`) so the welcome assets and history persistence are guaranteed on first paint. Sidebar membership is `sidebar_show: 'always'` plus a "last 5 opened" recents list persisted in `localStorage` under `last_opened_times_7768` (`PagesRouter.vue:138-166`). Separately, backend-registered applets (`app_state.registered_ext_applets`, declared at `App.vue:982`) get rendered through `AppletPage.vue` and appended to the same item lists (`PagesRouter.vue:123-133`) — this channel matters enormously in section (b).

The pages themselves, in descending order of investment:

**Homepage.vue** (2643 lines, 94KB — larger than the rest of the pages combined) is the fork's real front door and its most polished surface. A chat-style composer with a live CLIP token counter (`x/75`, `Homepage.vue:101-104`), recent-prompts dropdown (last 20 in `localStorage`, `Homepage.vue:905-920`), negative-prompt toggle, Ollama-backed random prompt, quick chips for Canvas (1:1 / 4:5 / 16:9), Quality (Fast 20-step ddim / Balanced 25-step karras / Detailed 35-step karras, `Homepage.vue:607-634`) and Batch (1/2/4). Below the composer: a "Your generations" strip, a 12-tile welcome carousel of hand-generated PNGs committed at `electron_app/src/assets/welcome/` (the README at `README.md:36` still says "six" — doc drift), an "Explore Styles" chip grid, and the tools grid driven by `categories: [["main","All AI Tools"],["pages","Pages"],["misc","Miscellaneous"],["tools","Tools"]]` (`Homepage.vue:634-639`) filtered from `router.all_applet_items` (`Homepage.vue:1111-1119`). Generation from Home is a queued handoff: `queuePromptForAutoGeneration` → `pendingPrompt` → a 700ms retry timer → `generatePrompt` builds `genOptions` and calls `stable_diffusion_manager.add_job` (`Homepage.vue:792-885`) — the user stays on Home while the SDManager queue runs. Arabic prompts are auto-translated before submission with a toast (`Homepage.vue:844-855`).

**Txt2Img.vue** (44 lines) and **Img2Img.vue** (80 lines) are thin shells over `SDImageGenerationApplet.vue` (260 lines) driven by the shared 441-line schema `electron_app/src/forms/sd_options_adv.json` — the frontend half of the dual form schema (the backend half is the 345-line JSON string in `backends/stable_diffusion/applets/options.py`). Img2Img adds the `send_to_img2img` cross-page handoff (`Img2Img.vue:32-45`) and input-image dimension sniffing.

**Inpainting.vue** (394 lines) is the most "app-like" of the legacy pages: mask canvas with brush-size slider, undo/redo stacks, keep/discard/retry post-generation box, drag-drop input — and, notably, **outpainting lives inside it**, dispatched on `sd_options.outpaint_function_name` (`Inpainting.vue:133`) via `utils/in_out_paint_utils.js`. The `outpainting.png` icon in `page_icon_imgs/` is an orphan from the era when upstream had a separate outpainting page (upstream issue #572 asks "Is outpainting removed from the app?"¹).

**PostProcessImage.vue** (144 lines, "Upscaler") is architecturally odd: it doesn't touch the Python backend at all — it invokes `window.ipcRenderer.invoke('run_realesrgan', …)` in the Electron main process (`PostProcessImage.vue:108`), caps input at 2048px, and renders into a two-slot `GenerationGallery`.

**ModelStore.vue** (277 lines) is the discovery surface: "My Models" vs "Available Models" card grids with background-image tiles, "Import From Computer" (local safetensors/ckpt → `convert_sd_to_tdict` post-process, `ModelStore.vue:154-195`), and a Refresh button. On mount it fetches the upstream catalog and merges FLUX.2 locally (`ModelStore.vue:109`). Gatekeeping is `utils/app_version.js:isModelDownloadAllowed`, which the fork has deliberately neutered to `!!(id && url)` with an explicit comment that it "should not block models on that legacy check" (`app_version.js:25-31`) — see section (d) for why that matters.

**PromptLibrary.vue** (939 lines) is the fork's second polished, modern page: hero panel with stat chips, an Ollama generator card (model detection, refresh, draft box, copy/save/open/generate-now), category filters and search over a built-in curated library (`prompt_library.js`), saved prompts and recents. `pageMeta.js:61` pitches it as "Browse, remix and generate prompts with Ollama".

**Training.vue** (409 lines) — **the page is a simulation.** `startTraining()` validates inputs and then calls `simulateTraining()` (`Training.vue:117-155`), a `setInterval` that increments a fake step counter every 500ms, cycling canned status strings ("Preparing dataset…", "Fine-tuning U-Net…", "Saving checkpoints…") and declaring "Training Complete! Model saved." after 1000 fake steps. No `send_to_py`, no `rapp`, no backend contact of any kind. It even hardcodes a `<select>` of sd15/sd21/sdxl base models that don't correspond to anything installed. The fork's own README admits it: "**DreamBooth Training UI** (frontend ready; backend integration coming soon)" (`README.md:29`). It sits in `home_category: 'main'` with no `sidebar_show` (`pageMeta.js:66-72`), so it appears in the Homepage "All AI Tools" grid but not the sidebar. Hold this against section (b), where the shipped binary turns out to contain a *real* training applet with the same title and the same icon.

**History.vue** (280 lines, eager) — Fuse.js prompt search, 30-per-page pagination, newest/oldest toggle, per-group delete, clear-all with native confirm, and a Share dropdown whose only entry is ArtHub.ai upload (`History.vue:50-57, 219-229`). Functional, legacy-styled (Bootstrap pagination with hand-rolled dark media queries).

**Settings.vue** (233 lines) is shockingly thin for an app of this ambition: exactly two settings — notification-sound toggle and an imgbb.com API key with show/hide eye (`Settings.vue:8-56`). No HF token field (the token only comes from `process.env.HF_TOKEN` via `native_functions.js:691-709`), no NSFW/content toggle (relevant to the packaged binary's "Change settings to enable NSFW content" stamp), no language selector — the Arabic toggle lives in the toolbar/menu, not Settings.

**Logs.vue** (38 lines) dumps `app_state.logs` as pre-line text; `sidebar_show: 'never'`, reachable from the toolbar help menu (`MainToolbar.vue:54`). **ContactUs.vue** (57 lines) is a fixed-position box with `diffusionbee@proton.me`. **BlankPage.vue** (31 lines) is an empty scaffold that isn't even registered in `pageMeta.js` — dead code.

The polish stratification is stark: **Homepage and PromptLibrary are the fork's own work** (modern, i18n-complete, token-aware CSS), while Txt2Img/Img2Img/Inpainting/History/ModelStore are inherited upstream surfaces with Arabic bolted on via inline `isArabic ? … : …` ternaries, and Training is a stage set.

## (b) The three apps within the app

### 1. The shipping renderer source

The renderer this repo builds believes the product is: Home → generate with SD-family models → inpaint/upscale → manage models → browse prompts → (pretend to) train. Its vocabulary is `applet`, `page`, `form_tags`, `tdict`. It carries icon assets for pages it doesn't have — `deforum.gif` and `interpolate.gif` sit in `electron_app/src/assets/imgs/page_icon_imgs/` next to `training.png` — because the renderer was forked from an upstream tree that *expects* backend-registered applets to arrive over the `utds` channel and materialize as pages. The mechanism is real and live: `AppletBase.init_applet` in `backends/stable_diffusion/applets/applets.py:41-55` pushes `registered_ext_applets.<name>.{title,description,icon,img_icon,home_category,inputs,outputs,is_stop_avail}` as `utds` state updates, and `PagesRouter.vue:11-20` + the `all_applet_items` computed render them with zero renderer-side code. The repo's *source* backend registers exactly one applet — `FrameInterpolator` ("Interpolator", "Generate videos by interpolating prompts and seeds", `frame_interpolator.py:40-46`, registered at `diffusionbee_backend.py:138`).

### 2. The packaged-binary superset — the repo cannot see its own shipped product

I dumped the PYZ table of contents of `electron_app/.packaged-backend/diffusionbee_backend` (1519 frozen modules) and diffed it against `backends/stable_diffusion/`. The binary contains, and the repo source lacks:

- **`applets.deforum`** — a real Deforum port: keyframe prompt parsing (`0:(prompt)` syntax, `parse_key_frames`), 2D camera warps via `cv2.warpPerspective` with rotation/zoom/movement expressions (default zoom `10*sin(2*3.14*t/100)`), histogram color matching between frames. Its UI metadata: `applet_title` **"Deforum Video"**, description "Generate animated videos with Deforum", icon `deforum.gif` (which the renderer ships!), and `home_category` set to **`video`** — a category that does not exist in this fork's Homepage `categories` list (`Homepage.vue:634-639`). With `sidebar_show` unset by the base class, **Deforum is unreachable in the fork's UI**: no sidebar entry, no Homepage section, no deep link. A shipped, functional feature with no door.
- **`applets.lora_training`** — a real LoRA trainer: `SDTrainer` over SD 1.x tdicts, dataset = folder of images + per-image `.txt` prompts ("Please provide more than 4 images with ground truth prompts"), `lora_rank` option, min 50 iterations, minSNR-weighted loss, RAM warning ("Training is very RAM intensive. Please close all other applications"), saves a `.tdict`. Its metadata: `applet_name` `lora_training`, title **"Training"**, icon **`training.png`**, `home_category` **`main`**. In the installed app, the Homepage "All AI Tools" grid therefore shows **two tiles, both titled "Training", both using `training.png`**: the fork's `Training.vue` simulator and the binary's real LoRA trainer rendered through `AppletPage`. (Upstream's own trainer is broken for some users — issue #580: "Trained model (.tdict) produces black image in Text to Image — v2.5.1"² — but it is real.)
- **`applets.merge_lora`** — "LoRA Tools" / "Merge LoRA weights with a base model" (safetensors LoRA + base model → merged output, ratio slider), home_category defaulting to `misc`.

- **`stable_diffusion.flux_generator`** plus a `flux_dylib.dylib` sitting next to the binary — the entire FLUX inference path (upstream 2.5.3's headline feature: "Support for Flux.1 image generation models… To use flux, scroll down to the bottom in the app home screen"³). The fork's renderer has no FLUX generation path at all (see (c) — the FLUX trap).
- **`stable_diffusion.utils.safety_checker`** (Yahoo OpenNSFW onnxruntime classifier, `open-nsfw.onnx`) and the unconditional scoring/stamping pipeline in the frozen `stable_diffusion.stable_diffusion.generate` — as established in today's brief; every decoded image is scored, and `safety_score > 0.8` with falsy `allow_nsfw` zeroes the array and cv2-stamps "NSFW content detected / Change settings to enable NSFW content". My own strings scan confirms `allow_nsfw` and `lora_tdict_paths` are fields of the frozen `sd_run`.
- **`stable_diffusion.plugins.prompt_enhancer`** (37KB of style presets; its default negative prompt literal is `#ugly, deformed, noisy, blurry, NSFW`), **`prompt_weighting`**, **`text_embeddings`** (textual inversion — 2.5.3's "Support for external textual inversion embeddings"³), **`infill_image`**, **`stable_diffusion.utils.nv_seed`**, and top-level **`lora_utils`**.

So the shipped product is a *superset*: video (Deforum, Interpolator), real LoRA training and merging, FLUX.1, embeddings, prompt enhancement — gated behind a renderer that either hides them (Deforum's homeless `video` category), duplicates them unknowingly (Training), or blocks them outright (FLUX). The fork has been building UI for a product it only half-possesses, because `scripts/prepare_backend_for_packaging.sh` treats `/Applications/DiffusionBee.app` as an opaque artifact.

### 3. The demo surfaces

Three non-shipping UIs reveal intent at three different moments. `serve:ui`/`AppDemoUI.vue` is a 14-line wrapper that mounts the **real** `App.vue` in a browser via `main_demoui.js` — but nothing stubs `window.ipcRenderer`, and `App.vue`'s `mounted()` calls the unguarded `send_to_py("strt")` (`App.vue:218`; `py_vue_bridge.js:90-91` does `window.ipcRenderer.sendSync` directly) long before `is_mounted` is set (`App.vue:241`). In a plain browser this throws, `mounted()` aborts, `is_start_screen` never clears — the "demo UI" likely stalls on the splash screen. (Flagged for R2 operational verification; `build:ui` compiling proves nothing about runtime.) `ai-image-studio.html` (683 lines, root) is a standalone indigo (`#6366f1`) "AI Image Studio" mock — the visual north star the redesign recon keeps referencing, never wired to anything. `docs/design/inspiration-hub-mockup.html` (200 lines, Tailwind + Lucide CDN) is an older, simpler vision whose sidebar (Home, Txt2Img, Img2Img, Inpainting, Models, History, Settings) predates Prompt Library, Training, and the Upscaler as peers. Three demos, three eras, none of them the shipping UI.

## (c) Onboarding journeys

**First-run model setup has quietly changed shape since the settled claims were written.** `check_and_prompt_model_download()` (`App.vue:507-534`) **no longer opens the modal**: if models exist it silently completes onboarding and runs the (console-only) hardware report; if none exist it merely logs "No models found — onboarding is available from the Home screen." The modal is now user-initiated: Homepage's `needsOnboarding` banner (shown when `availableModels` is empty and `onboarding_completed` isn't set, `Homepage.vue:1230-1234`) → `startOnboarding()` → `app.launchOnboarding(true)` (`Homepage.vue:1108-1112`, `App.vue:608-628`) → `show_model_setup = true` + `fetch_models_list()`. The overlay itself (`App.vue:48-150`) is the settled flow: catalog fetch keyed by `get_instance_id` (`App.vue:538-539`), FLUX.2 merge (`App.vue:551`), `isSelectableOnboardingModel` filter, `pickOptimalOnboardingModel(…, { preferFlux2: true })` (`App.vue:556-559`), one-click download with 300ms polling, success state, optional-download checkboxes, Skip, and the `onboarding_completed` / `optional_downloads_offered` flags in `app_data_2.json`. A 5-second retry timer re-checks after mount (`App.vue:282-284`).

**The FLUX trap — the sharpest defect chain in the app.** `preferFlux2: true` means any machine with ≥13GB RAM and no HF token gets **FLUX.2-klein-4B** (7,751,105,712 bytes, `flux2_catalog.js:21`) as its *recommended first model* (`model_selection.js:284-290`). The user downloads 7.75GB, lands on Homepage, types a prompt — and `generatePrompt` hard-refuses: `isFlux2Model(selectedAsset)` → toast "FLUX.2 is downloaded, but the current generation backend supports Stable Diffusion models only. Pick an SD model…" (`Homepage.vue:836-841`). The fork ships a catalog it labels generatable (`GENERATABLE_MODEL_TYPES` includes `flux2_model` and `flux_nnc`, `flux2_catalog.js:71`), a picker that prefers FLUX.2, and a generator that blocks it — while the packaged binary contains a complete `flux_generator` the renderer never invokes. Upstream, meanwhile, has no FLUX.2 at all (issue #576, "Consider supporting flux2-dev", Nov 2025²): the fork is simultaneously *ahead of upstream* and *behind its own backend*.

**HF-token gating is doubly invisible.** The token is read only from the main-process environment (`native_functions.js:691-709`: `process.env.HF_TOKEN`), exposed over the `get_hf_token` sync IPC, and consumed by `enrichFlux2Model`, which returns `null` for `requires_hf_token` models when no token exists (`flux2_catalog.js:84-87`) — so FLUX.2-klein-9B and FLUX.2-dev silently vanish from ModelStore and onboarding for every normal DMG user. Settings.vue has no field for it; no page mentions it.

**ModelStore discovery** is a flat card wall — no search, no size display (upstream issue #575 asks for exactly that²), no architecture badges; the only per-model metadata line is `model_metadata_to_str`. The fork's `build_number` is `0029` (`electron_app/package.json:4`), which is *below* the live catalog's `min_version` gates for community SDXL tdicts (36) and FLUX.1 (40) — the fork only sees those models because `isModelDownloadAllowed` was rewritten to ignore `min_version` (`app_version.js:29-31`). Correct call, fragile reasoning: the fork's build number claims to be older than its own binary.

**Training page entry** is the journey that isn't: Homepage grid → "Training" tile → a beautiful three-step DreamBooth form → an 8.3-minute fake progress bar → "Model saved." Nothing is saved. The real trainer (binary `lora_training`) appears — in the installed app — as a *second*, identically-titled tile.

**Installed-app vs dev-mode gap.** Beyond the settled bridge-resolution story: the installed `/Applications/diffusion-sd-ui.app` runs the packaged binary (so its users see the Interpolator/Deforum/LoRA-Training/Merge-LoRA applets materialize, and get NSFW-stamped images because the old renderer never sent `allow_nsfw`), while the dev-mode source backend has none of those modules and no safety checker — two genuinely different products. The update checker compounds it: `check_for_updates` (`App.vue:467-493`) phones **upstream's** `checkupdates.diffusionbee.com` with the instance id and would send users to `package.json`'s `website` — `https://diffusionbee.com` (`electron_app/package.json:5`). It is dormant only because the live server currently answers `1.7.4_0024` (verified today⁸) and `24 > 29` is false; if upstream's server ever reports build ≥30, every fork user gets prompted to "update" to the competitor's product. Dev mode instead fires `alert("Not checking for updates.")` on every launch (`App.vue:220-224`).

## (d) Web primary sources

**diffusionbee.com**⁴ markets "The Ultimate Suite of Creative AI Tools" — Text to Image, Generative Fill, **Video Tools**, Image to Image, Image Upscaler, **Image Variants**, **Train Models**, Control Images, **Illusion Generator** — plus an "AI canvas" co-pilot, "runs 100% offline", macOS 13.1+ (Apple Silicon recommended, Intel "very slow"). Download is **macOS-only**. Three of those nine headline tools (Video, Variants, Illusion) and the canvas have no trace in this fork's renderer. The "Train models on your data… 100% locally" pitch is precisely the feature the fork mocks in `Training.vue` and the binary actually ships.

**Upstream repo**⁵: 13.6k stars, 725 forks, 384 issues, **issue creation restricted**, 277 commits, AGPL-3.0, README features "SD 1.x, SD 2.x, SD XL, Inpainting, ControlNet, LoRA". **Last push 2024-10-30** (GitHub API) — upstream is dormant; issue #568 (Jun 2025) asks outright "Has Divam Gupta abandoned this project?"² Releases tell the divergence story: **2.2.1** (Jun 2023) shipped "Completely new UI, queue, Video tools - interpolation, Deforum, infinite AI canvas, LoRA tools"³; **2.5.3** (2024-08-14, two macOS DMGs only — arm64 291MB, Intel 327MB) shipped FLUX.1 (arm64/macOS 13+, "scroll down to the bottom in the app home screen"), textual-inversion embeddings, "Ability to block NSFW images", and a reorganized models page³. Those four 2.5.3 bullets map one-to-one onto the binary-only modules I found: `flux_generator`, `text_embeddings`, `safety_checker`, and the catalog's `min_version` gates. **The repo this fork builds is, in backend terms, a pre-2.5.3 tree wrapped around a post-2.5.3 binary.**

**Live catalog**⁶: 26 models — 9 legacy SD 1.x safetensors (DreamShaper, CyberRealistic, Deliberate, ReV Animated, GhostMix, Samaritan 3D Cartoon, Dreamlike, moDi, Game Icon Institute; all `post_process: convert_sd_to_tdict`), SDXL Base 1.0 (`min_version` 29), 13 community SDXL 8-bit tdicts (`min_version` 36; Juggernaut family, RealVis, Animagine, epicrealismXL, Pony Realism, protovisionXL, dynavisionXL…), and FLUX.1-schnell/dev (`min_version` 40, `type: flux_nnc`). **No FLUX.2** (the fork's local merge is the only source), **no Default_SD1.5** (the fork's `FALLBACK_SD15_MODEL` points at `huggingface.co/divamgupta/stable_diffusion_mps`⁷, `model_selection.js:3-11`), and no `size_bytes` on any upstream entry — only the fork's FLUX.2 entries carry sizes. The catalog skews to Civitai community models including three Pony-derived SDXLs — exactly the class of model that makes the binary's unconditional OpenNSFW scoring consequential.

**Positioning delta.** Upstream 2.5.3 is a macOS-only, dormant, FLUX.1-capable product whose update server is stale (`1.7.4_0024`). This fork (2.4.0+build 0029, `net.aldoy.diffusion-sd-ui`) differentiates on: Windows NSIS installers with a bundled default model (upstream has no Windows line at all), Arabic/RTL with Tajawal (the only SD GUI in this class with a first-class Arabic journey — prompt auto-translation included), a curated 12-image welcome carousel of self-generated assets, a documentation/screenshot discipline (`docs/screenshots/`, `ensure_doc_screenshots.sh` which *fails on placeholder content*), Ollama prompt generation, and FLUX.2 downloads. But it trails its own binary (FLUX generation, Deforum, real training, embeddings) and its version string understates its backend. The fork's honest self-assessment is hiding in plain sight in the README: "DreamBooth Training UI (frontend ready; backend integration coming soon)" — written, apparently, without knowing the backend already arrived.

## Cross-cutting surprises (candidates for R2 stress-testing)

1. **Two "Training" tiles, one grid, same icon** — the fake page and the binary's real `lora_training` applet collide in the installed app's Homepage "All AI Tools" section.
2. **Deforum is shipped but unreachable** — its `home_category: 'video'` has no Homepage section in the fork and no sidebar entry; the renderer even bundles its `deforum.gif` icon.
3. **The FLUX trap** — onboarding prefers FLUX.2 (`preferFlux2: true`), Homepage refuses to generate with it, and the binary could run FLUX.1 today if the renderer ever asked.
4. **PagesRouter mounts everything** — "lazy" pages all instantiate hidden at startup; laziness is only webpack code-splitting.
5. **The update checker points at upstream** — dormant by numeric accident (`0029 > 0024`), one upstream server edit away from redirecting the fork's users to diffusionbee.com.
6. **`serve:ui` is probably splash-locked** — no `ipcRenderer` stub in browser mode; `App.vue:218` throws before `is_mounted`.
7. **Settings is a two-knob page** — no HF token, no content-policy toggle (the binary's NSFW stamp references a setting that has never existed in any renderer), no language selector.

## Open questions for R2

- In the installed app, do `lora_training`/`merge_lora`/`deforum` applets actually register at runtime (they should — `register_applet` calls live in the binary's entry script)? A runtime capture of `registered_ext_applets` would settle reachability empirically.
- Does the Txt2Img path (`SDImageGenerationApplet`) send FLUX.1 `flux_nnc` models to the binary successfully (the binary routes by model type), or is all FLUX generation dead in the fork?
- What does `verifyModelsHardwareCompatibility` (`App.vue:800+`) cost/buy beyond console output — is any of it surfaced anywhere?
- Is `serve:ui` genuinely broken in-browser, and does anyone rely on it (AGENTS.md recommends it for UI work)?
- Should the fork's `build_number` be bumped past 40 to match its binary — and should the update URL be repointed or severed?
